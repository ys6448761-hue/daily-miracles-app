## Context-Adaptive Behavior — `has_car=true` + odongdo

**Example: user types "자차로 오동도도 가려고요"**

### Frontend (immediate — no API call):
- parseContext detects: hasVehicle=true, nextPlace='odongdo' → stateIndex=2
- JourneyFlow: 🚗자산 → 🚡(10분) → 🏔돌산 → ··· → 🌿오동도("동선 확인 중")
- FOR_ME card: "자산 하차 후 오동도 입구까지 도보 약 5분. 케이블카 + 오동도 합산 반나절(3~4시간) 코스입니다."
- SOUL_DISCOVERY primaryText: "오동도까지 이어가신다면 자산 쪽을 동선 후보로 먼저 볼 만해요..." (hardcoded)
- DEPTH: shows odongdo route paragraph

### On form submit (API call):
- explicit_context = { has_car: true } (odongdo chip does NOT send place_code — SAFE_RESTRICTION)
- Backend _applyExplicitContextChip: supplements soulContext.has_car=true if GPT missed it
- For discovery intent: _generateSoulMessage factors has_car + people_type → companion acknowledgement

**Key finding:** The meaningful context response (JourneyFlow, FOR_ME, SOUL_JUDGMENT text) comes from **local hardcoded texts indexed by stateIndex** — not backend runtime. The backend explicit_context improves discovery recommendation scoring, but does NOT change what the cablecar page renders: all driven by local stateIndex.

## Special Items Re-verified

**ESSENTIAL_INFO drift (operating_hours vs opening_hours_json):**  
CONFIRMED. travelGuideService serializes `p.opening_hours_json` as string to `operating_hours`. PlaceBasicInfo reads `place.operating_hours`. SoulCableCarPage reads `placeData.opening_hours_json` directly as object. Two different parsing paths. Future travelGuideService field-mapping changes silently break SoulCableCarPage._fmtHours.

**explicit_context.place_code SAFE_RESTRICTION:**  
CONFIRMED. SoulCableCarPage.jsx:324-328 never includes place_code in explicit_context. Text-based detection via PLACE_ALIAS_MAP wins for cablecar.

**Human Experience NOT implemented in 0503ed8:**  
CONFIRMED. No HEL content in any .js/.jsx. WISH_SCENE hidden by onError.

**"내 여정에 담기" disabled:**
